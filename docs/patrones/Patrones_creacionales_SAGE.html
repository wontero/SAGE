1. Introducción y contexto técnico de SAGE

SAGE (Sistema de Análisis y Gestión Energética) es una plataforma web unida a un dispositivo IoT. El dispositivo, basado en un ESP32 con dos sensores INA219 y un selector de fuente, mide tensión, corriente, potencia y energía de la rama solar y de la red, y decide qué fuente alimenta la carga (modos Solar, Red y Automático). La plataforma recibe esas mediciones, genera alertas, envía órdenes de cambio de modo, registra el consumo facturado por la distribuidora y simula escenarios económicos (red, solar y mixto) para apoyar la decisión de invertir en energía solar.

El stack definido para el proyecto es Blazor Web App sobre .NET 10 (C#), con MudBlazor y Blazor-ApexCharts en la interfaz, Entity Framework Core sobre SQL Server Express 2022 para los datos y firmware en Arduino (C++) para el ESP32. Por eso los ejemplos de este documento están en C#, salvo el del firmware, que está en C++.

Los patrones creacionales resuelven cómo se crean los objetos: separan al código que usa un objeto de la decisión de qué clase concreta instanciar, cómo armarlo o cuántas instancias deben existir. Este documento identifica y clasifica los cinco patrones creacionales clásicos (Gamma et al., 1994) y aplica a SAGE los tres que resuelven problemas reales del proyecto: Abstract Factory, Builder y Singleton, sobre las clases del modelo (ControladorMonitoreo, Simulacion, ControladorFuente, etc.).

Alcance. SAGE está en desarrollo (Scrum, Sprints 0–3, del 23/10 al 12/12 de 2026). Las aplicaciones que se describen son decisiones de diseño sobre el modelo actual; el impacto en la calidad se presenta como impacto esperado junto con la forma de medirlo, no como un resultado ya observado.

2. Identificación y clasificación de los patrones creacionales

El catálogo de Gamma, Helm, Johnson y Vlissides (el "GoF") define cinco patrones creacionales. Se pueden clasificar con dos criterios: el ámbito (si la variación se resuelve con herencia entre clases o con composición de objetos) y la pregunta de creación que responden.

PatrónÁmbitoPregunta que respondeIntención
Factory MethodClase (herencia)¿Qué clase concreta se crea?Definir un método para crear un objeto y dejar que las subclases decidan qué clase instanciar.
Abstract FactoryObjeto¿Qué familia de objetos se crea?Crear familias de objetos relacionados que deben usarse juntos, sin nombrar sus clases concretas.
BuilderObjeto¿Cómo se arma un objeto complejo?Separar la construcción paso a paso de un objeto complejo de su representación final.
PrototypeObjeto¿A partir de qué ejemplar se crea?Crear objetos nuevos copiando un objeto existente (prototipo) y modificando lo necesario.
SingletonObjeto¿Cuántas instancias existen?Garantizar una única instancia de una clase y un punto de acceso global a ella.

Una segunda forma de agruparlos es por el mecanismo: Factory Method y Abstract Factory delegan la creación en una fábrica (el cliente pide, la fábrica decide la clase); Builder y Prototype se ocupan de la configuración del objeto (por pasos o por copia); Singleton controla el ciclo de vida. Además de los cinco del GoF, en la práctica se usa la fábrica simple (un método estático con un switch), que no es un patrón GoF pero suele ser el primer paso antes de un Factory Method, y la inyección de dependencias, que en .NET reemplaza buena parte de los usos clásicos de Singleton y de las fábricas.

3. Patrones aplicados a SAGE

Se aplican los tres patrones que responden a una necesidad concreta de SAGE. Cada uno se presenta con una ficha (problema concreto en SAGE, solución y participantes), un diagrama de clases simplificado y un fragmento de código. Los nombres de clases y métodos salen del diagrama de clases del modelo de SAGE en StarUML; las clases nuevas que introduce cada patrón se indican en el texto.

3.1. Abstract Factory

Caso de usoMonitorear dispositivo y cambiar modo de operación (ControladorMonitoreo, ControladorTelemetria, ControladorOrdenes).
ProblemaEl equipo decidió construir primero la plataforma (inicio de sesión, pantallas y datos de prueba) y conectar el hardware después. Las pantallas de monitoreo, alertas y control necesitan dos objetos que trabajan juntos: uno que entrega mediciones y otro que envía órdenes al dispositivo. Esos dos objetos tienen que ser de la misma "familia": no tiene sentido leer mediciones simuladas y mandar órdenes a un ESP32 real, o al revés.
SoluciónUna interfaz IFabricaDispositivo crea el lector de telemetría y el canal de órdenes. FabricaDispositivoReal crea objetos que leen las Medicion guardadas por la API de telemetría y dejan la Orden pendiente para que el ESP32 la consulte. FabricaDispositivoSimulado genera mediciones con una curva solar de prueba y confirma las órdenes al instante. La familia se elige en un único lugar, al iniciar la aplicación.
ParticipantesFábrica abstracta: IFabricaDispositivo · Fábricas concretas: FabricaDispositivoReal, FabricaDispositivoSimulado · Productos abstractos: ILectorTelemetria, ICanalOrdenes · Productos concretos: dos por familia · Clientes: ControladorMonitoreo, ControladorOrdenes, ControladorAlertas.
public interface IFabricaDispositivo
{
    ILectorTelemetria CrearLector();
    ICanalOrdenes CrearCanalOrdenes();
}

public class FabricaDispositivoSimulado : IFabricaDispositivo
{
    public ILectorTelemetria CrearLector() => new LectorTelemetriaSimulado();
    public ICanalOrdenes CrearCanalOrdenes() => new CanalOrdenesSimulado();
}

public class FabricaDispositivoReal(SageDbContext db) : IFabricaDispositivo
{
    public ILectorTelemetria CrearLector() => new LectorTelemetriaBD(db);
    public ICanalOrdenes CrearCanalOrdenes() => new CanalOrdenesBD(db);
}

// Program.cs: la familia se elige una sola vez, por configuración
if (builder.Configuration["Dispositivo:Modo"] == "Simulado")
    builder.Services.AddScoped<IFabricaDispositivo, FabricaDispositivoSimulado>();
else
    builder.Services.AddScoped<IFabricaDispositivo, FabricaDispositivoReal>();

Las pantallas y controladores solo conocen IFabricaDispositivo, ILectorTelemetria e ICanalOrdenes. El paso del Sprint con datos de prueba al Sprint con el ESP32 conectado se reduce a cambiar un valor de configuración. La misma fábrica simulada sirve en las pruebas automáticas de alertas y órdenes, que así corren sin hardware.

3.2. Builder

Caso de usoSimular escenarios económicos, incluido en Gestionar parámetros económicos (PantallaSimulacion, ControladorSimulacion).
ProblemaUna Simulacion necesita muchos datos de distintas fuentes: la empresa, los consumos facturados de varios períodos (ConsumoFacturado), la versión vigente de ParametrosEconomicos, la potencia a instalar (kWp) y el horizonte en años. Con todo eso calcula costoRed, costoSolar, costoMixto y recuperacionAnios. Un constructor con siete parámetros es fácil de llamar mal, y además hay reglas: la potencia debe ser positiva, el horizonte razonable, y si hay pocos meses de consumo la pantalla tiene que mostrar una advertencia (PantallaSimulacion.mostrarAdvertencia).
SoluciónSimulacionBuilder recibe los datos paso a paso con métodos de nombre claro y, en Construir(), valida, calcula los tres escenarios y devuelve una Simulacion que ya no se modifica. ControladorSimulacion cumple el papel de director: sabe en qué orden reunir los datos.
ParticipantesBuilder: SimulacionBuilder · Director: ControladorSimulacion · Producto: Simulacion · Datos de entrada: ConsumoFacturado, ParametrosEconomicos.
public class SimulacionBuilder
{
    private Empresa? empresa;
    private List<ConsumoFacturado> consumos = [];
    private ParametrosEconomicos? parametros;
    private decimal potenciaKWp;
    private int horizonteAnios = 10;

    public SimulacionBuilder ParaEmpresa(Empresa e) { empresa = e; return this; }
    public SimulacionBuilder ConConsumo(IEnumerable<ConsumoFacturado> c) { consumos = c.ToList(); return this; }
    public SimulacionBuilder ConParametros(ParametrosEconomicos p) { parametros = p; return this; }
    public SimulacionBuilder ConPotencia(decimal kWp) { potenciaKWp = kWp; return this; }
    public SimulacionBuilder ConHorizonte(int anios) { horizonteAnios = anios; return this; }

    public Simulacion Construir()
    {
        if (empresa is null || parametros is null)
            throw new InvalidOperationException("Faltan la empresa o los parámetros vigentes.");
        if (consumos.Count == 0) throw new InvalidOperationException("No hay consumo facturado.");
        if (potenciaKWp <= 0) throw new ArgumentOutOfRangeException(nameof(potenciaKWp));
        if (horizonteAnios is < 1 or > 25) throw new ArgumentOutOfRangeException(nameof(horizonteAnios));

        var sim = Simulacion.Calcular(empresa, consumos, parametros, potenciaKWp, horizonteAnios);
        if (consumos.Count < 12)
            sim.Advertencias.Add("Menos de 12 meses de consumo: el resultado es orientativo.");
        return sim;
    }
}

// En ControladorSimulacion (director)
var simulacion = new SimulacionBuilder()
    .ParaEmpresa(empresa)
    .ConConsumo(consumosDelAnio)
    .ConParametros(parametrosVigentes)
    .ConPotencia(3.0m)
    .ConHorizonte(10)
    .Construir();

3.3. Singleton

Caso de usoControl de la fuente en el dispositivo (firmware: ControladorFuente, SelectorFuente) y monitoreo en tiempo real en la plataforma.
ProblemaEn el firmware: el ESP32 tiene un solo relé selector. Si dos partes del programa (el ciclo automático y la atención de una orden remota) usaran dos instancias distintas de ControladorFuente, cada una con su propio modo, fuenteActual y esperaReintentoS, podrían mandar posiciones contradictorias al mismo relé. En la plataforma: el estado en vivo de cada dispositivo (último contacto, fuente activa) se actualiza con cada envío de telemetría y lo leen todas las sesiones abiertas de la pantalla de monitoreo; tiene que ser el mismo objeto para todos.
SoluciónEn el firmware, un Singleton clásico de C++ (instancia estática local, constructor privado, copia prohibida), que además evita memoria dinámica en un microcontrolador. En la plataforma no se escribe un Singleton a mano: se registra la clase en el contenedor de inyección de dependencias de .NET con duración Singleton, que garantiza una instancia por aplicación y sigue siendo reemplazable en las pruebas.
ParticipantesSingleton (firmware): ControladorFuente, que usa el único SelectorFuente · Singleton gestionado (plataforma): EstadoDispositivosEnVivo · Clientes: ControladorTelemetria (escribe), ControladorMonitoreo (lee).
// Firmware ESP32 (Arduino, C++)
class ControladorFuente {
public:
  static ControladorFuente& instancia() {
    static ControladorFuente unica;     // se crea una sola vez, sin memoria dinámica
    return unica;
  }
  ControladorFuente(const ControladorFuente&) = delete;
  void operator=(const ControladorFuente&) = delete;
  void conmutarA(Fuente f);
private:
  ControladorFuente() {}
  Modo modo = AUTOMATICO;
  Fuente fuenteActual = RED;
};

// loop(): ControladorFuente::instancia().conmutarA(SOLAR);
// Plataforma (.NET): una instancia compartida, segura entre hilos
public class EstadoDispositivosEnVivo
{
    private readonly ConcurrentDictionary<int, EstadoDispositivo> estados = new();

    public void Actualizar(int dispositivoId, EstadoDispositivo e) => estados[dispositivoId] = e;
    public EstadoDispositivo? Obtener(int dispositivoId) =>
        estados.TryGetValue(dispositivoId, out var e) ? e : null;
}

// Program.cs
builder.Services.AddSingleton<EstadoDispositivosEnVivo>();

El caso principal es el del firmware, donde la unicidad la impone el hardware. El de la plataforma es un complemento: en .NET no se implementa el patrón a mano, se delega al contenedor. Un Singleton nunca debe recibir por inyección un servicio de duración menor, como el DbContext de EF Core (que es scoped): quedaría "capturado" y se compartiría entre usuarios. Por eso EstadoDispositivosEnVivo solo guarda datos en memoria; lo persistente sigue pasando por la base de datos.

La tabla recorre los escenarios de creación de objetos que aparecen en los casos de uso de SAGE. Incluye escenarios donde la conclusión es no usar ningún patrón, porque un patrón sin una variación real que resolver solo agrega clases.

5. Comparación de patrones

Se comparan los tres patrones aplicados con los criterios pedidos (eficiencia, mantenibilidad y aplicabilidad) más dos que influyen en la decisión: la complejidad que agregan y la facilidad para probar el código.

CriterioAbstract FactoryBuilderSingleton
Eficiencia en ejecuciónDespreciable; un objeto fábrica extra.Un objeto intermedio por construcción; despreciable.Ahorra instancias; si hay estado compartido, exige sincronización.
MantenibilidadAlta para cambiar de familia; baja para agregar un producto (cambia todas las fábricas).Alta: agregar un dato opcional no rompe llamadas existentes.Baja si es estático: acopla y oculta dependencias. Media con DI.
Aplicabilidad en SAGEdispositivo real vs simulado (central en el plan de Sprints).simulación económica.firmware (relé único) y estado en vivo.
Complejidad añadidaAlta: interfaces por cada producto y por familia.Media: una clase builder.Baja.
TestabilidadMuy buena: la familia simulada sirve para tests.Muy buena: las validaciones se prueban aisladas.Mala si es estático; buena con DI.

Lectura de la comparación. En SAGE ningún patrón creacional afecta de forma apreciable el rendimiento: los cuellos de botella están en la base de datos y en la red (telemetría del ESP32), no en la creación de objetos. La decisión se toma por mantenibilidad y testabilidad. Abstract Factory es el que más estructura agrega, pero es el que más valor da en este proyecto porque sostiene la estrategia de construir la plataforma antes que el hardware. Singleton es el que más fácil se usa mal; por eso se limita al firmware y, en la plataforma, al contenedor de inyección de dependencias.

6. Mejores prácticas de selección e implementación

  1. Empezar sin patrón. Introducir una fábrica cuando aparece la segunda variante real (un segundo formato, una segunda familia), no "por si acaso". En SAGE, Usuario, Empresa y Alerta se crean con constructor.
  2. El cliente depende de interfaces. Las fábricas devuelven IDocumentoReporte, ILectorTelemetria, ICanalOrdenes; las pantallas nunca hacen new de una clase concreta de infraestructura.
  3. Elegir la variante en un solo lugar. La familia de Abstract Factory y las duraciones de los servicios se configuran en Program.cs y en appsettings.json, no en las pantallas.
  4. En .NET, preferir el contenedor de DI a los Singleton estáticos. AddSingleton, AddScoped y AddTransient resuelven el ciclo de vida sin acoplar el código a una propiedad estática, y permiten reemplazar la instancia en pruebas.
  5. Un Singleton debe ser seguro entre hilos y no capturar dependencias de menor duración (por ejemplo, el DbContext). Usar colecciones concurrentes o estado inmutable.
  6. Builder: validar en Construir() y devolver un objeto que no cambie. Así no puede existir una Simulacion a medio armar o inválida.
  7. Firmware: memoria estática. En el ESP32, evitar new dentro de loop(); el Singleton con instancia estática local no fragmenta la memoria.
  8. Nombrar y documentar. Nombres que revelen el rol (SimulacionBuilder, FabricaDispositivoSimulado, ControladorFuente::instancia()) y el patrón anotado en el diagrama de clases del modelo.
  9. Probar cada creación. Una prueba por builder (casos válidos e inválidos), una por fábrica concreta y pruebas de los controladores con la fábrica simulada.

7. Casos de estudio

Los casos 1 y 2 son casos de diseño dentro de SAGE: describen la situación, la aplicación del patrón, el impacto esperado en la calidad según las características de ISO/IEC 25010 y cómo se va a verificar durante los Sprints. El caso 3 muestra el uso de estos mismos patrones en el framework que usa el proyecto.

Caso 1. De datos de prueba al dispositivo real (Abstract Factory)

Situación. El plan de trabajo prioriza la plataforma: el Sprint 1 cubre inicio de sesión y pantallas con datos de prueba, y el dispositivo físico se integra después. Sin un diseño previsto, cada pantalla de monitoreo, control y alertas tendría condiciones para distinguir datos falsos de reales, y el día de integrar el ESP32 habría que revisarlas todas.

Aplicación. IFabricaDispositivo con las familias simulada y real (sección 3.1). Las pantallas se escriben una sola vez contra las interfaces.

Impacto esperado. Mantenibilidad (modificabilidad): el cambio de familia queda en un archivo. Testabilidad: las reglas de alertas y órdenes se prueban sin hardware. Fiabilidad: se evita mezclar mediciones simuladas con órdenes reales.

Cómo se verifica. Al integrar el dispositivo, contar los archivos modificados fuera de la infraestructura (objetivo: solo Program.cs y la configuración) y comprobar que las pruebas de alertas siguen pasando con la fábrica simulada.

Caso 2. Simulaciones siempre válidas (Builder)

Situación. La simulación cruza el consumo facturado con los parámetros económicos. Un dato faltante o fuera de rango (potencia cero, horizonte de 100 años) produciría proyecciones absurdas que podrían llegar a la gerencia.

Aplicación. SimulacionBuilder concentra todas las validaciones y la advertencia por pocos meses de datos (sección 3.2).

Impacto esperado. Fiabilidad: no se pueden crear simulaciones inválidas. Usabilidad: la advertencia aclara cuándo el resultado es orientativo. Testabilidad: cada regla tiene su prueba.

Cómo se verifica. Pruebas unitarias del builder con un caso válido y un caso por cada regla incumplida.

Caso 3. Los mismos patrones dentro de .NET

El framework que usa SAGE aplica estos patrones en sus propias APIs, lo que muestra su utilidad en un proyecto de gran escala:

  • Builder: toda aplicación ASP.NET Core arranca con WebApplication.CreateBuilder(args), que configura servicios, configuración y registro paso a paso antes de builder.Build(). También StringBuilder y DbContextOptionsBuilder de EF Core.
  • Abstract Factory: DbProviderFactory de ADO.NET crea conexiones, comandos y parámetros de un mismo proveedor de base de datos (por ejemplo, SQL Server) sin que el código cliente nombre las clases concretas.
  • Singleton gestionado: la duración Singleton del contenedor de inyección de dependencias, usada por el propio framework para servicios como la configuración y el registro de logs.

8. Conclusiones

  • Tres patrones creacionales resuelven problemas reales de SAGE: Abstract Factory en el acceso al dispositivo, Builder en la simulación económica y Singleton en el control del relé del ESP32.
  • El de mayor impacto es Abstract Factory, porque permite desarrollar y probar toda la plataforma antes de tener el hardware, que es justamente el orden de trabajo elegido por el equipo.
  • En .NET varios patrones vienen resueltos por el lenguaje o el framework (por ejemplo, el contenedor de DI); conviene usar esos mecanismos antes que implementaciones manuales.
  • Tan importante como aplicar un patrón es saber cuándo no hacerlo: las entidades simples de SAGE se crean con constructores.
  • El impacto en la calidad se verificará durante los Sprints con las pruebas y métricas indicadas en cada caso de estudio.
